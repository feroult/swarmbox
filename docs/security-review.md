# Security review of the host helper (slice 7.3)

Date of the review: 2026-11-08. Reviewer: the build's implementer (an AI agent), reading the code line by line; no human
reviewed it, and no third party audited it. Treat this as a first written review, not as an audit. Design references: section
11 (security model), D16 (POSIX sh), D26 (the helper comes from the signed image), D28 (tunnel token), 3.3 (the `up` lock),
3.7.1 to 3.7.3.

## Scope

Reviewed, with the files read in full for the parts named here:

- `container/host/swarmbox-host` (POSIX sh, about 2250 lines): configuration (`config`, `env`), `create-flags`, `fingerprint`,
  `up`, `reset`, `stop`, `url`, `update`, `remote`, the connector step, the lock, the temporary files, `eval` use, the
  extraction of the helper from the image.
- The shell function templates `container/host/templates/{bash,zsh,fish}` (the bootstrap that extracts the helper) and
  `container/scripts/swarmbox-init.sh` (which quotes values into the function block).
- `cloudflare-setup.py` as the `remote` wrapper's back end: temporary and config files, the connector image, the tunnel token.

Not reviewed, out of scope: the container side (`serve`, tools, the shim), the web terminal, Cloudflare's services, Podman itself,
and the signing of the image (release preparation, `.github/workflows/release.yml`). macOS and a real WSL were not available
(see "Limits").

## Threat model used

The helper runs as the host user with that user's privileges. The people who can change its inputs are: the user (command line,
environment, config file); other accounts on the same machine (they can only act through folders that are writable by them, so
the review asks "does the helper put anything in a folder others can write?"); and the image the user chose (it supplies the
helper archive that `update` and the function extract, and the helper that is then run). A hostile image is not defended against
beyond refusing a malformed archive: it already supplies code that the host runs next (D26). A hostile account that is the same
user is not defended against.

## Findings

Severity: high (host compromise from unprivileged input), medium (a guard of the design can be bypassed by crafted input),
low (hardening, a local-account concern), info (reviewed, no defect, recorded with its residual limits). Status: `fixed` means
the code changed and a regression test fails without the change; `documented` means no code change, with the reason in the
decision log entry `[7.3]`. No row is open. Test names are `file::Class.test` in `tests/`.

## Tools and results

- `shellcheck -s sh container/host/swarmbox-host container/scripts/swarmbox-init.sh`: no findings (shellcheck 0.9.0, the one
  installed on this box, run 2026-11-08; the files are in the CI list of `ci.yml`). `shellcheck -s bash container/host/templates/bash`
  reports two notes that are intended: SC2015 (`A && B || C` on the `mkdir`/`mktemp` guard, where `C` is the failure message) and SC2088
  (a literal `~` is matched on purpose). The zsh and fish templates cannot be checked by shellcheck.
- Behavior tests: `tests/test_security_review.py` runs the real helper and the real script against the fake Podman, on `mktemp`
  folders only. The planted-symlink tests learn the helper's pid from a wrapper that `exec`s it, so the planting happens before
  the helper's first step.

## Limits of this review

- No real macOS, no real WSL and no Podman older than 4.3 were available; behavior that differs there (the BSD `stat` and
  `find` forms of the mode check, `mktemp -d` templates, `chmod` on `/mnt`) is `[unverified]`.
- The real registry, real image signing and a real Cloudflare account were not used.
- The review is of the code as of this commit. A change to the helper needs the adversarial tests of
  `tests/test_security_review.py` to be run again (`tests/run_all.sh` runs them).
- Not reviewed: the container side, the tools, the web terminal, and Podman's own handling of the flags the helper builds.
